# データ量と品質を並行して高める運用 v0.1

作成日：2026-09-19
状態：運用方針をYuichiが承認（2026-09-19）、Codex直接調査方式への変更を承認（2026-09-20）

## 目的

1人の不明点をすべて解決するまで全体を止めず、出典で確認できた項目を小さなバッチで積み上げる。未確認項目は同じ人物の確認済み項目から分離し、CANDIDATEに保留する。

この方針は調査量を増やすための運用であり、QA、HUMAN APPROVAL、Master承認を省略しない。

## バッチ単位

- 1バッチは原則10〜20人。
- 1回の調査Waveは1〜6人で調整し、標準4人から試す。詳細は[調査人数の適応運用](RESEARCH_BATCH_SIZING_V0.1.md)に従う。
- B.LEAGUE公式選手プロフィールを入口にする。
- 高校、大学、プロ所属は、各組織・大会・競技団体の公式資料を優先する。
- 高校時代の名簿確認では、ウインターカップとU18日清食品トップリーグの大会公式メンバー表を優先的に横断する。
- 『月刊バスケットボール』の選手名鑑・進路記事は上位参考資料として候補発見と不足項目の補助に使用し、発行元・版・ページまたは資料内位置を残す。
- 難しい人物だけを別の例外キューへ分離する。
- Batch 001で測った形式を再利用し、人物ごとに独自形式を作らない。

- そのうち福岡第一高等学校出身者が確認できた場合は、必ず調査対象に含める。
- 福岡第一高等学校以外の高校出身者も幅広く対象に含め、特定の高校に偏らないようにする。

- Wave対象クラブの選定では、Master（現所属Career）とCANDIDATE（Batch/Waveの現所属Career）の両方を確認し、既にいずれかで現所属をカバー済みのクラブと重複しないよう調整する。

## Wave種別とカデンス（2026-09-23〜）

Yuichiの指示（2026-09-23）により、Waveを以下の2種類に分け、一定のカデンスで交互に実施する型を定める。

- **新規開拓Wave（Acquisition Wave）**: 未収録の人物をCANDIDATEとして新規追加するWave。これまでのWave 1〜3はすべてこの型。
- **深掘りWave（Enrichment Wave）**: 既存の公開済み人物（Master／CANDIDATE問わず）について、既存Careerレコードで保留（HOLD）になっているフィールドの追加調査、および「現所属クラブのみ」登録によって欠落している過去の所属歴（CLUB_HISTORY_SCOPE issue該当分）の追加調査を行うWave。新規人物の追加は行わない。

**カデンス**: 新規開拓Waveを3回実施するごとに、深掘りWaveを1回挟む（3:1）。Batch 007はWave 1〜3が新規開拓3回連続だったため、Wave 4は深掘りWaveとし、Wave 5以降で新規開拓を再開する。

**深掘りWaveのデータ構造**: 深掘りWaveは新しいWaveフォルダ（例: `wave_04`）として追加するが、対象は既存のPerson/Career/Organizationであり、既存レコードのIDや値は変更しない。追加調査で得た情報は以下のいずれかの形で追記する。

1. 既存Career（他Waveのentity_id）に対する追加のevidence_records行と、新しいqa_decisions行（reviewed_atを新しくし、必要ならeligible_fieldsを拡張）。旧いqa_decisions行は削除・上書きしない。
2. 新たに判明した所属歴（現所属クラブ以前の中間クラブ等）は、新規Career IDを採番してcareer_candidates.csvに追加する。

**深掘りWaveの優先対象**:
- HOLD_CANDIDATE判定のCareer（`organization_id`自体が単独の専門媒体情報のみで未確認のもの）を優先し、独立した第2ソースを探す。
- READY_FOR_VERIFIED_REVIEWだが`start|end`が保留のCareer（高校・大学の卒業/在籍期間未確認）について、公式または準公式ソースでの期間確認を試みる。
- CLUB_HISTORY_SCOPE issue（B7I0010→B7I0012→B7I0013）が立っている人物の、卒業後〜現所属クラブ加入までの中間所属歴。

## 1人あたりの最小確認範囲

1. Personの氏名
2. 出身高校または直前組織
3. 大学または最初のプロ所属
4. 各Careerのrole
5. 項目別のSourceと資料内位置
6. 表記揺れ、期間、人物同定等の未解決事項

生年月日、身長、体重、ポジション等は公式資料で確認できる場合だけ候補に含める。Person / Career / Organization / Sourceの中心設計を拡張せず、追加属性は項目別Evidenceとして保持する。

## 項目単位の判定

| 判定 | 扱い |
| --- | --- |
| READY_FOR_VERIFIED_REVIEW | 公式資料の該当箇所で値を直接確認でき、未解決の矛盾がない。Yuichiのレビュー対象へ送る |
| HOLD_CANDIDATE | 出典不足、矛盾、人物同定、組織不明等がある。CANDIDATEに残す |
| REJECT_CANDIDATE | 別人、誤記、無関係資料等が判明した。理由を残して採用対象から外す |

同じ人物でも、確認できた項目はREADY、期間等の未確認項目はHOLDに分けられる。人物全体を一括で確定しない。

## 高速化する部分

- B.LEAGUE、クラブ、JBA、大学連盟の公式URLをCodexが直接確認する。
- ウインターカップ、U18日清食品トップリーグの大会公式ロスターを同一世代の複数選手に再利用する。
- 『月刊バスケットボール』の名鑑を調査入口として利用し、掲載値と公式資料の一致・差異を項目単位で記録する。
- 公式プロフィールから定型項目を抽出する。
- URL、取得日、発行元、項目名を定型CSVへ記録する。
- ID重複、参照切れ、必須項目、日付順、判定値をPythonで検査する。
- 同じ公式資料を複数人で再利用する場合も、項目ごとの該当位置を残す。
- 公式資料が見つからない人物だけをFelo・Geminiの例外調査へ送る。
- Claudeは各人物の検索ではなく、10〜20人分が揃った後のバッチQAに使用する。

## 人間が確認する部分

- 同姓同名や表記違いの人物同定
- 複数資料が矛盾する場合の採否
- VERIFIED候補の差分と出典
- HUMAN APPROVALの対象版・範囲
- Masterへの反映

## 調査の停止条件

公式プロフィール、所属組織、大会・競技団体の主要資料で確認できなければ、そのバッチではHOLDとする。検索結果が増えない状態で同じ人物の調査を続けず、例外キューへ移す。

二次資料だけの値は、一次資料が見つかるまでCANDIDATEに留める。『月刊バスケットボール』の名鑑・進路記事も有力な参考資料として保存するが、それだけで公式確認済みとは表示しない。推定した入学年・卒業年、所属継続、役割の引継ぎは登録しない。

## バッチ完了条件

- 全人物の確認対象項目がEvidenceまたはIssueに結び付いている。
- Python構造検査がPASSしている。
- READY、HOLD、REJECTの件数を報告できる。
- HOLDが残っていても、理由と次の確認先が記録されていればバッチを区切れる。
- VERIFIED、HUMAN APPROVAL、MASTERを自動で更新していない。

## 既知の課題：候補データサイトのcardContext表示（2026-09-23発見、未修正）

`scripts/build_site_candidate_data.py`が生成する候補データの`cardContext`（一覧カードに出る「期間 ・ 所属」表示）は、各人物のCareerの中から機械的に「最新」を1件選ぶロジックになっているが、次の理由で正しく機能していないケースがある。

- 現所属クラブのCareerは、B.LEAGUE公式ロスター一覧など「今季の在籍」を示すだけの資料しかなく、start/endが未記録（HELDではなく単に情報自体がない）ことが多い。
- 一方、高校・大学のCareerはWikipedia等でstart/endの西暦が明記されていることが多い。

現行ロジックはstart/endが両方空欄の場合を「期間未確認」として扱い、これを暗黙的に「もっとも新しい」と誤判定してしまうため、実際には引退済み・卒業済みの学校名がcardContextに出て、現役の所属クラブが表示されないことがある（例：富樫勇樹の高校が新規Career追加前後で入れ替わって表示され、本来は「2015年〜・千葉ジェッツ」であるべきだった）。

2026-09-23にこの場で「end年をもとに最新を判定する」修正を一度試みたが、逆に「start/endが明記された過去の学校歴」が「start/endが未記録の現所属クラブ」より新しいと誤判定されるケースが新たに発生したため、副作用が大きいと判断してこの場では revert し、現行ロジック（バグを含むが影響範囲を把握済み）のまま据え置いた。修正には「このCareerは現在進行形かどうか」を判定できる情報（現所属クラブフラグ、シーズン表記の解析など）が別途必要であり、Yuichiの判断のもとで設計してから着手すべき事項として記録する。CANDIDATEデータの`careers`配列自体（各Careerの内容）には影響しておらず、あくまで一覧カードの要約表示（cardContext）のみの問題である。
