# FUTURE ARCHITECTURE — Draft v0.1

## 文書の位置づけ

この文書は、検索・機械向けJSON/API・Data Factoryの将来方針をまとめた設計案である。Governance v1.0を変更せず、スキーマ拡張、大量取込、個別データの承認、Master反映をこの文書だけで許可しない。

2026年9月18日の[共有会話](https://chatgpt.com/share/6aace9c0-5080-83ee-9a7f-7c4ce9ab169e)を検討材料とした。そこで提案された「The社史型」という呼び方を、人間向けWebと機械向け構造化データを同じデータから提供する設計思想の略称として用いる。共有会話のAI回答は人物・経歴等の史実を裏付けるSourceとして使用しない。外部サービスの仕様をそのまま複製するものでもない。

## プロダクトの方向性

Japan Basketball Archiveは、人物名鑑だけではなく、次の関係を時間軸と出典からたどれるアーカイブを目指す。

```text
Person → Career → Organization
   │          │          │
   └──────── Source ─────┘
```

長期候補としてTeam / Competition / Game / Statsを検討する。ただし現在のデータ設計v0.1はPerson / Career / Organization / Sourceのままとし、追加エンティティはパイロット確認後に別途合意する。

同じ承認済みデータから、次の出力を生成する。

- 人物・組織のWebページ
- 検索と関係探索
- 機械向けJSON/API

WebページとAPIを別々に手入力しない。候補データを公開する場合は、VERIFIEDやMASTERと誤認されない状態表示を付ける。

## 検索の段階

### Phase 1：基本検索

人物名と組織名を検索し、人物・組織・出典へ移動できるようにする。現在の少数プロトタイプで使いやすさを確認する。

### Phase 2：絞り込みと関係探索

データ量と品質が十分になった後、年代、都道府県、ポジション、所属経路、プロ経験などを候補として評価する。「福岡第一から特定大学へ進んだ人物」のように、文章の部分一致ではなくID間の関係を検索する。

同じOrganizationに同じ期間所属した人物をCareerから算出し、中学・高校・大学・プロクラブの「同時所属」「同一ロスター」を探索できる機能も候補とする。所属期間が不明な人物を推測で結び付けず、使用したCareerとSourceへ追跡できるようにする。詳細は[同時所属・チームメイト関係機能案](TEAMMATE_RELATIONSHIP_PROPOSAL_V0.1.md)に記録する。

### Phase 3：自然言語検索

自然言語をAIが検索条件へ変換し、構造化データベースから結果を取得する。AIが未登録の経歴を生成して回答する方式にはしない。検索結果から使用したデータとSourceへ追跡できるようにする。

## 機械向けJSON/API

将来は一覧と個別詳細を分け、必要なデータだけ取得できる構成を検討する。

```text
/api/players.json
/api/organizations.json
/api/players/P000030/index.json
/api/players/P000030/profile.json
/api/players/P000030/career.json
```

パスと分割単位は例であり、正式仕様ではない。公開前にspec_version、公開対象、利用条件、更新方法、Source表現を合意する。

## Sourceと事実の対応

出典はページ単位でまとめるだけでなく、どの事実をどの箇所が裏付けるか追跡できるようにする。

最低限の候補項目は次のとおり。

- Source ID
- 発行元、資料名、URLまたは原資料参照先
- 該当ページ、シート、行、本文箇所
- 確認日
- 裏付けるPerson / Career / Organizationと項目
- 矛盾、表記揺れ、確認上の注意

信頼度をランク化する場合も、ランクだけで採用を自動決定しない。

## Data Factoryの流れ

```text
公式資料・公開資料
        ↓
RAW → CANDIDATE → QA → VERIFIED
        ↓                 ↓
   差戻し記録       HUMAN APPROVAL
                          ↓
                        MASTER
                          ↓
              Web / Search / JSON API
```

AIは資料探索、抽出、重複・矛盾確認、形式検証を支援する。Yuichiの明示的承認なしにVERIFIEDをMASTERへ自動昇格させない。MASTER更新を契機にWeb等を生成する場合も、承認対象の版と範囲が一致していることを確認する。

## 進める順序

1. 福岡第一高校Excelの列・出典・不明点を確認する。
2. データ設計v0.1への対応を合意する。
3. 小規模なCANDIDATE作成とQA記録の形式を決める。
4. PythonでID、参照、必須項目、形式を検証する。
5. 少数バッチで処理時間、差戻し理由、誤りを測る。
6. 結果を見て基本検索とJSON出力の実装範囲を決める。
7. 人数と対象組織を段階的に拡大する。

先に大量投入せず、小規模バッチで再現性と追跡性を確認してから拡大する。

## 評価指標の候補

- Source付きCareer候補の作成件数と所要時間
- 項目別に出典箇所を追跡できる割合
- 人物同定・表記揺れ・期間矛盾の未解決件数
- QA差戻し率と主な理由
- 自動検証で検出できた問題件数
- Human verification後の訂正率

処理速度だけを目標にせず、出典追跡と訂正率を同時に確認する。件数目標はパイロットの実測後に決める。

## 今回行わないこと

- Person / Career / Organization / Sourceを超えるスキーマ拡張
- 大規模なデータ一括取込
- 検索基盤や外部データベースの導入
- 公開JSON/APIの実装
- VERIFIEDまたはMASTERへの昇格
